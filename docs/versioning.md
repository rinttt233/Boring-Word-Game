# 版本与发布规范

> 本文件是版本流程的唯一约定来源；发版时同时更新 `VERSION`、`CHANGELOG.md` 与归档目录。

## 一、什么时候生成版本号

| 场景 | 是否发版 | 说明 |
|---|---|---|
| 用户明确指令（"发版 1.3""生成版本号"） | ✅ 发版 | 唯一触发条件 |
| 新系统 / 新玩法循环 / 大批内容（一个阶段） / 架构变更 | ⏳ 提醒 | agent 主动建议发版，等用户点头 |
| 功能增补、UI 批次、文档补充 | ⏳ 提醒 | 视体量判断，通常攒 1~2 批后建议发版 |
| bug 修复 / 文案 / 数值微调 | ❌ | 只做批次备份，随下次发版并入 |

**日常改动**：复制受影响文件到 `_refactor_backup/<批次名>_<时间戳>/` 即可，不写版本号。

## 二、版本号怎么递增

- `X.Y`：大修改批次 —— 次版本 +1（例：1.3 → 1.4）
- `X.Y.Z`：小修补 —— 修订号 +1（例：1.3 → 1.3.1），发版时加 `--patch`
- 基线：**1.3.1**（品位接入 · 单元扩容 · 拆除复用 · 记忆口径 · 副产物积压）。1.0 / 1.1 为开发期里程碑，未正式归档。
- **下一版本参考号：1.4**（按 `docs/roadmap.md`，预计为「电力优先级 + 储能」，并含 A13 电力库存上限/自放电）
- 注：1.3.1 按小修补号发布，但实际含新内容与新机制（主线 13→14 条）；如需语义对齐，下次发版可改为 1.4。

## 三、发版动作清单（agent 执行）

1. （可选门禁）`python -X utf8 -m unittest discover -s tests` 与 `main.py --gui-selftest` 通过
2. `python -X utf8 release.py <版本> "<主题>" [--check]`
   - 归档全量源码 → `_refactor_backup/v<版本>_<时间戳>/`（排除 `saves/`、`__pycache__/`、`_refactor_backup/`、`releases/`）
   - 写 `VERSION`
   - 在 `CHANGELOG.md` 插入版本条目骨架（幂等：已有条目则跳过）
   - **复制整个工作区 → `releases/v<版本>/`（规则第 10 条）**
3. 补全 `CHANGELOG.md` 三节：**主要改动 / 影响范围 / 验证**
4. 向用户汇报更新报告（批次清单、影响范围、验证结果、归档与发布快照路径）

## 三·补、工作区发布快照（规则第 10 条）

每次发版后，把**工作区内的全部文件**复制到工作区下的独立文件夹：

```
<工作区>/releases/v<版本>/        ← 发布快照（与当次源码逐文件一致）
```

要点与注意事项：

- **必须排除该文件夹自身**，否则会出现 `releases/v1.3/releases/v1.3/releases/...` 的递归嵌套。
  脚本通过黑名单实现：`SKIP_DIRS = {__pycache__, saves, _refactor_backup, releases, .git}`。
- 同时排除：存档目录 `saves/`、批次备份 `_refactor_backup/`、字节码 `__pycache__/` 与 `*.pyc`。
- 同名版本重复发版时**先清空该目录再复制**，保证快照与当前代码一致（幂等）。
- 快照用途：可直接拷走/压缩分发、与当前工作区做逐文件对比、作为"该版本可运行副本"。
- 两个目录的分工：
  | 目录 | 作用 | 命名 |
  |---|---|---|
  | `_refactor_backup/vX.Y_<时间戳>/` | 发版归档（历史留痕，可多次） | 带时间戳 |
  | `releases/vX.Y/` | 工作区内发布快照（每版本一份，可运行） | 仅版本号 |

## 四、更新报告要求

- 列出本版本包含的批次（按主题归类，不逐条罗列琐碎改动）
- 标明**影响范围**：玩法/内容/界面/存档兼容性（存档结构是否变化）
- 给出**验证**：单测数量与结果、GUI 自检、端到端脚本、关键实测数据
- 给出**归档路径**与**下一版本参考号**

## 五、存档兼容性提示

发版说明中若涉及以下变化，必须显式标注"旧存档可能不兼容"：
- `core/` 内核数据结构字段增删
- 各 system 的 `to_dict/load` 字段语义变化
- content 中 id 的改名或删除（设施/物质/条目/配方）
