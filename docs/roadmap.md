# 制作顺序与分批建议（平衡/内容改造）

> 清单条目见 `docs/balance_proposals.md`。本文件只回答"**先做哪个、每批做什么、怎么验收**"。
> 规则不变：**每批开始前备份、每批结束跑回归并停下汇报、不擅自发版**。

---

## 一、排序依据

1. **先测量后改数**：批次 0 先做成本/容量基线脚本，后面所有数值调整都以它为基准（避免拍脑袋）。
2. **先修"压力消失"的三处根因**：单元供给（批次 1）→ 记忆/维护（批次 2）→ 副产物（批次 3）。这三处是本项目当前"中后期只剩排队"的直接原因。
3. **依赖优先**：电力优先级要能保护"维护/生产/可选"三类负载，因此排在维护系统之后（批次 4）。
4. **同主题合并**：回收/拆解（A6+B4+B5）共用 industry 与建造面板代码，合成批次 5。
5. **数值打磨靠后**：品位、事件预警、时间尺度（批次 6）会改动全局乘数，放在主体机制稳定后。
6. **扩展内容可插拔**：远圈风险/物流（批次 7）无硬依赖，可按时间提前或推后。
7. **收尾统一**：结算与 QoL（批次 8）需要前端埋点齐备，放最后；其中**统计埋点要提前在批次 1 就加**，避免返工。

```
批次0 基线脚本
   └─▶ 批次1 单元经济+效率科技 ──▶ 批次2 记忆/维护压力 ──▶ 批次4 电力优先级+储能 ──▶ 批次6 数值打磨 ──▶ 批次7 远圈风险/物流
                                    └─▶ 批次3 副产物积压+出口（与批次2并行亦可）        └─▶ 批次8 结算+QoL
                    批次5 回收/拆解生态（依赖批次1，可与批次2/3 并行）
```

## 三、分批详情

### 批次 0 · 基线测量（A9）
- 新增 `tools/cost_audit.py`（**只读**，不接入运行时）：把 23 条恢复条目成本、43 种设施建造费折算成"设施·秒 + 单元·秒"，输出每条目的**最小设施数需求**与**单元占用峰值**；同时导出当前 `slots` 需求总和 vs 单元上限。
- 验收：脚本抽 3 项与人工手算一致；输出留档 `docs/baseline_report.md`（供批次 1/2 定系数）。
- 风险：无（不改运行时代码）。

### 批次 1 · 单元经济 + 效率科技（C1 = A5 + B3）★核心
**批次0 的实测结论改变了本批的实现形式**：43 个设施中只有 3 个是多槽
（`solvent_extractor` / `large_coal_plant` / `fluid_power_plant`），因此
"有效槽位 = ⌈slots/ef⌉" 对单元瓶颈几乎没有缓解作用。故本批把效率科技实现为
**产能与节拍倍率**（同样单元数产出更多、作业更快），而不是字面意义的槽位合并。

**实际实现（已完成）**
- `core/units.py`：`UnitPool.efficiency`（默认 1.0，随存档读写、旧档缺字段按 1.0）、
  `set_efficiency()`（下限 0.1）、`effective_slots(slots)`、`staff_factor(assigned, slots)`。
- `staff_factor = 1 + (ef - 1) × min(1, assigned/slots)` —— **ef = 1.0 时恒为 1.0**，
  严格保持既有平衡基线；派员不足时按比例只拿部分加成。
- `content/recovery.json`：新增 4 条**可选**条目（总线复用 +0.25 / 指令预取 +0.25 /
  并行作业编排 +0.5 / 单元自主决策 +0.5），字段 `grants.unit_efficiency`，
  效能上限 1.0 → 2.5。选可选而非主线的原因：主线链条（`database.is_complete()` 要求
  所有非 optional 条目固化）与 `victory_test.py` 的 10 条主线清单保持稳定，回归不失真；
  如需升级为主线，需同步更新 `victory_test.py` 的主线清单。
- `systems/recovery.py`：`grant_total(key)` / `unit_efficiency()` / `_sync_efficiency()`；
  在 start、作业完成（恢复/固化）、TTL 过期、记忆崩溃、读档五个时机同步到 `UnitPool`，
  并写日志（提升=normal，回落=warn）。作业耗时 ÷ 效能。
- `systems/industry.py`：`_staff_factor()` 统一用于生产与 `power_balance()`；
  **输入与输出同乘**（化学配比不变，只是更快），提取耗电、燃烧耗料同步缩放；
  `assign` 的单元上限改用 `effective_slots()`（多槽设施在高效能下只需更少单元即可满负荷）。
- `systems/memory.py`：加固作业耗时 ÷ 效能。
- `core/stats.py`（新）：运行统计埋点（停摆次数/时长、加固、恢复、固化、崩溃、单元与效能峰值、
  运行时长），`Engine` 持有并随存档读写；只加计数，不参与任何玩法判定 —— 供批次8 结算与统计面板。
- **顺带修掉一个既有 bug**：`industry.tick` 原先每 tick 先无条件清除停摆状态、再由各 tick
  函数重新判定，导致"停摆/恢复"日志与统计逐 tick 抖动（实测 40 tick 产生 80 次停摆事件）。
  现已由各 tick 函数自行报告真实状态。
- UI：单元面板显示"效能 ×N / 在役·运转·空闲"；建筑详情显示"效能 → 产能·节拍倍率与满负荷所需单元数"；
  百科科技词条新增"效果"行（自动读取 `grants`）。

**验收**：新增 `tests/test_unit_efficiency.py`（16 例：效能换算 / 槽位折算 / 加成同步与丢失 /
产能与耗料同乘 / 提取耗电缩放 / 派遣上限 / 作业提速 / 存档与旧档兼容）；全量 93 例单测 OK；
`main.py --gui-selftest` 通过；端点脚本 `smoke/gameplay/chain/power/tlb/tlc/tld/tle/victory` 全 OK。

### 批次 3 · 副产物积压 + 多种应对（A3 + B6）
**做什么**：积压判定（`content/` 配置阈值）+ **不少于 4 种应对**：
1. **转化**：新增 recipes 把多余副产物转成有用的（焦炉煤气/煤焦油 → 氢/苯/沥青/溶剂延伸）；
2. **放空/焚烧**：放空塔（消耗副产物，产少量电或纯销毁）；
3. **回注/堆存**：回注井/堆场（按速率存入地块，带容量或时限 → 空间压力）；
4. **自动降速政策**：积压超阈值降速（可开关，日志告警）；
配套：物料页显示积压警示条。
**验收**：新增 `tests/test_byproduct_backlog.py`（阈值判定/放空/回注速率/自动降速）；`chain_test.py` 回归（焦炉线最敏感）。
**风险**：连锁停摆 → 用"降速而非停机"作为默认，玩家可自选更严政策。

### 批次 1.5 · 建造耗时作业（A11）★已完成
**机制**：`build` 不再是瞬时落地，而是**占用一个执行单元的施工耗时作业**。
- `IndustrySystem.build()`：先判空闲单元（无 → 拒绝且不扣资源）→ 扣材料（失败则退料并归还单元）
  → 建设施并置 `under_construction=True` → 开一条 `kind="build"` 的作业，时长 = 设施 `build_time`
  （5~30 游戏秒；缺字段时用 `default_build_time=8.0`）。
- 建造中：不产出、不耗料、不计入电力预算、不可分配单元（`assign` 明确报"仍在建造中（剩余 Ns）"）。
- 完工：`job_done` → `under_construction=False`，单元由作业队列归还，**不会自动派员**（保持原有节奏）。
- 撤销：施工中 `undo` 会中止作业、回收施工单元、全额返还材料并还原地块；已产出设施仍禁止撤销。
- 读档兜底：`tick` 发现"建造中但找不到作业"会自动置为完工（自愈）。
- 调试旁路：`IndustrySystem.instant_build`（`dbg instant [on|off]`）与 `install_instant()`；
  端点脚本聚焦产线数值时开启，**gameplay_test 走真实耗时路径**。

### 批次 2 · 记忆 / 维护压力（C3 + A1 + A2 + D6轻量）★已完成
**2a 记忆压力曲线（A1/C4）**：`content/memory.json` 改为
`劣化 = 0.02/s + 0.002/s × 已永久固化条目数 + 0.004/s × 运转设施数`；
加固恢复改为**按完整度分档**（<40 → +32；<70 → +25；否则 +16）。
效果（见 `docs/baseline_report.md` 第 4 节）：空厂 83 分钟归零、2.9 次加固/小时；
终局（13 条固化 + 22 台运转）12 分钟归零、19.3 次加固/小时 —— 记忆成为贯穿全局的斜线。
压力台阶变化时会限频提示（"劣化速率上升至 …"）。

**2b 维护/待机消耗（A2 + C3）**：新增 `systems/maintenance.py` + `content/maintenance.json`。
- **知识门控**：恢复主线条目 `db_upkeep`「设备维护与检修工艺包」后体系才启用 ——
  前期不背维护包袱，中期开始"规模有代价"。（未恢复时 `demand_per_sec` 恒为 0、无任何日志噪声。）
- 新增物质 `maintenance_kit`「维护件」+ 配方 `make_maintenance`（钢 0.05/s + 残骸合金 0.12/s
  → 维护件 0.3/s）+ 设施 `maintenance_depot`「维护站」（需 db_upkeep；造价 残骸 20 + 钢 8）。
- 消耗：运转 100%、**停着（无单元）33%**、**封存 0%**；供得上 → 设备状态回升（0.5/s），
  供不上 → 下滑（0.03/s）→ 低于 75 起按概率故障（0 时约 50%/分钟）→ **故障停机** 25s
  → 抢修恢复至 40（仍易故障）。停机经 `Facility.halt_until/halt_reason` 这一通用接口生效。
- **封存/解封**：`mothball <设施> [on|off]` + 建筑面板按钮；封存释放单元且零消耗，
  解封需一个空闲单元 + 10s 重启（防"来回白嫖"）。
- UI：状态栏新增「维护件 x.x (需求/s) 设备最低状态」；建筑行/详情显示设备状态、
  停机剩余、封存标记；`memory` 命令追加维护摘要；百科新增 设定《维护：规模是有代价的》
  与 教程《维护件供不上怎么办》，并更新 记忆劣化 / 执行单元 / 停摆排障 / 建造排障 四篇。

**验收**：新增 `tests/test_build_time.py`（13 例）与 `tests/test_pressure.py`（17 例）；
全量单测 **123 例 OK**；`--gui-selftest` 通过；9 个端点脚本全 OK；
`victory_test` 额外覆盖"恢复 db_upkeep → 建维护站 → 产维护件（0.3/s 供 0.15/s 需求）"。

**顺带修复**：`industry.tick` 原先每 tick 先无条件清除停摆状态、再由各 tick 函数重新判定，
导致"停摆↔恢复"日志与统计逐 tick 抖动（40 tick 产生 80 次停摆事件）—— 批次1 已改为由各
tick 函数报告真实状态。
